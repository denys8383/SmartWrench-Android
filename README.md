# SmartWrench - AI-Assisted OBD2 Car Diagnostic App

## Опис ідеї 
**SmartWrench** — це розумний мобільний додаток для автомобілістів та ентузіастів, який виводить діагностику авто на новий рівень. На відміну від стандартних сканерів, які видають лише сухі P-коди помилок, додаток пов'язує виявлену проблему з конкретною конфігурацією автомобіля (наприклад, 2.0-літровий бензиновий двигун) та надає детальну покрокову інструкцію з ремонту. 

Додаток також включає інтегрованого AI-асистента, який отримує прихований контекст несправності та допомагає користувачеві підібрати інструменти, оцінити ризики та розібратися у складностях ремонту.

**Обрана індустрія:** Автомобільна сфера.

## Основні функціональні вимоги
1. **Автоматичне підключення та зчитування даних:** Додаток встановлює з'єднання з діагностичним адаптером (на базі ELM327) для зчитування кодів несправностей з ECU. *(Примітка: в рамках поточного MVP та для демонстрації логіки розробки, модуль підключення реалізовано через Mock-об'єкт).*
2. **Управління профілем ("Мій Гараж"):** Створення, редагування та збереження профілю автомобіля (марка, модель, рік, об'єм та тип двигуна) для забезпечення точності інструкцій.
3. **Контекстна розшифровка помилок:** Зіставлення коду несправності (DTC) з активним профілем авто та генерація конкретної покрокової інструкції з ремонту.
4. **Інтелектуальний AI-асистент:** Вбудований чат на базі LLM, який автоматично отримує контекст помилок автомобіля для надання персоналізованих консультацій щодо ремонту.
5. **Автономність базових функцій:** Збереження історії зчитаних помилок та інструкцій для доступу в офлайн-режимі (в гаражі або на трасі без інтернету).

# SmartWrench AI Diagnostics (MVP)

Мінімальна працездатна версія (MVP) мобільного AI-додатка для діагностики несправностей автомобіля за кодами помилок (OBD2 DTC). Проєкт складається з мобільного клієнта на Android (Kotlin) та бекенду на Python (FastAPI).

---

## Архітектура та стек технологій
* **Мобільний клієнт:** Android (Kotlin, Jetpack Compose / XML, Retrofit, Coroutines).
* **Бекенд:** Python, FastAPI, Pydantic, Uvicorn.
* **AI-компонент:** Експертна система на основі правил (rule-based) для аналізу кодів несправностей двигуна (наприклад, специфіка 2.0L бензинових двигунів).

## Лабораторна робота №4: Локальні дані мобільного застосунку

### Що реалізовано
У мобільний застосунок **SmartWrench** додано постійне локальне сховище історії діагностики автомобіля на базі **Jetpack DataStore** та **Gson**:
- Автоматичне збереження завершених запитів після успішної відповіді backend-сервера зі статусом `готово`.
- Відображення списку історії у зворотному хронологічному порядку (найновіші запити зверху) та обробка стану порожньої історії.
- Перегляд повних деталей будь-якого обраного запису (локальний ID, дата й час, код DTC, пробіг, рівень небезпеки та повна рекомендація AI).
- Видалення окремого запису або повне очищення історії з обов'язковим діалоговим вікном підтвердження (`AlertDialog`).

### Фактичний потік даних (Data Flow)
1. **Введення:** Користувач вводить код помилки (`dtcCode`) і пробіг (`mileage`) у `MainActivity` та натискає кнопку аналізу.
2. **Мережевий запит:** Клієнт `Retrofit` (`SmartWrenchApi`) у фоновому потоці `Dispatchers.IO` надсилає POST-запит на локальний сервер `http://10.0.10.163:8000/`.
3. **Валідація та збереження:**
   - Якщо сервер повертає валідну непорожню відповідь (`severity` та `recommendation`), UI показує результат, формує об'єкт `DiagnosticRecord` зі статусом `"готово"` і передає його у `historyManager.saveRecord(record)`.
   - Якщо виникає мережевий збій або помилка backend, спрацьовує блок `catch`: користувач бачить повідомлення про помилку, а запис у локальне сховище **не зберігається**.
4. **Реактивне оновлення UI:** `HistoryManager` записує оновлений JSON-список у файл DataStore. Підписка на `historyFlow` у `MainActivity` автоматично отримує оновлений список і перемальовує блок історії на екрані.

- **Обраний варіант:** Варіант А — Архітектура всередині мобільного клієнта (`Mobile Architecture`).

### 2. Короткий опис архітектурних змін
Код мобільного застосунку розділено на три незалежні шари з чіткими межами відповідальності:
- **Domain Layer (`DomainLayer.kt`):** Містить доменні моделі (`DiagnosticInput`, `DiagnosticPrediction`), типізовані помилки (`DomainError`), інтерфейс репозиторію (`DiagnosticRepository`) та бізнес-сценарій `AnalyzeDtcUseCase`.
- **Data Layer (`DataLayer.kt`, `SmartWrenchApi.kt`, `HistoryManager.kt`):** Містить мапер `DiagnosticMapper` та дві взаємозамінні реалізації інтерфейсу: `RealDiagnosticRepository` (мережевий запит через Retrofit) і `FakeDiagnosticRepository` (локальна імітація для тестів та автономної демонстрації)[cite: 20, 21, 22].
- **Presentation Layer (`PresentationLayer.kt`, `MainActivity.kt`):** Містить `DiagnosticUiState`, `DiagnosticViewModel` із передачею залежностей через конструктор (`DiagnosticViewModelFactory`) та UI-екран, який лише підписується на `StateFlow`.

## Розвиток AI-функціональності (Лабораторна робота №6 — Варіант А)

У межах Лабораторної роботи №6 реалізовано **Варіант А (Розширення наявної AI-функції)**:
1. **Нові ознаки вхідного контексту:** Додано вибір типу силової установки (`engineType`: `Бензин`, `Дизель`, `Гібрид`) та поле опису симптомів автомобіля (`symptoms`).

## Джерело AI-моделі, вимоги до доступу та безпека даних

- **Місце виконання AI:** 
  1. **Основний режим (`RealDiagnosticRepository`):** Локальний backend-сервер на базі `FastAPI` (`POST http://10.0.10.163:8000/analyze`), який формує промпт з урахуванням коду DTC, пробігу, типу двигуна та симптомів і звертається до LLM API / експертної бази правил.
  2. **Автономний режим (`FakeDiagnosticRepository`):** Вбудований детермінований провайдер на боці клієнта, який дозволяє повністю перевірити всі сценарії застосунку та запустити автоматизовані тести без доступу до зовнішньої мережі.
- **Зберігання API-ключів та безпека:**
  - Усі секрети та API-ключі до зовнішніх AI-сервісів зберігаються виключно поза кодом мобільного застосунку (у файлі `.env` на стороні backend-сервера, який додано до `.gitignore`).
  - Мобільний клієнт не містить жодних токенів або ключів у вихідному коді чи в локальному сховищі `DataStore`.
  - Для демонстрації та тестування використовуються виключно синтетичні дані (стандартизовані коди OBD-II та тестові показники пробігу).
